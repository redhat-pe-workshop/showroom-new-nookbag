== Analysis Overview

*Workshop*: Platform Engineering Workshop +
*Current State*: 7 modules, 49 adoc files, ~3,300 lines, nearly full-day workshop +
*Analysis Date*: 2026-02-03 +
*Status*: High-quality content with uneven pacing - heavy educational content in Modules 6-7

== Key Findings

=== Strengths
- Solid narrative arc (Parasol insurance company storyline)
- Good hands-on activities in Modules 2-5
- Comprehensive coverage of RHDH capabilities
- Well-structured GitOps-based configuration approach

=== Issues Identified
1. *Module 1* is 100% narrative with zero hands-on activities
2. *Module 6* (Supply Chain Security) is 7,458 words and 55% conceptual/educational
3. *Module 7* (Continuous Improvement) is 4,869 words and 65% conceptual
4. *Significant repetition* in GitOps workflows (~5 occurrences of same pattern)
5. *Incomplete optional content* (module-06.3.1 is just a TODO placeholder)
6. *Heavy concept introductions* that could link to external docs instead

== Identified Repetitive Patterns

=== 1. GitOps/Argo CD Configuration Loop (~5 occurrences)
Pattern:

- Edit values.yaml file in GitLab
- Uncomment configuration block
- Commit changes
- Refresh Argo CD application
- Wait for pod restart
- Verify changes

*Found in*: m2.3, m2.4, m2.5, m4.2, m7.2

=== 2. Dynamic Plugin Enable Pattern (~4 occurrences)
Pattern:

- Locate comment marker in values.yaml
- Uncomment plugin configuration
- Commit changes
- Refresh GitOps
- Verify deployment

*Found in*: m2.4, m2.5, m4.2, m7.2

=== 3. Login/Account Creation Variations (~6 occurrences)
Pattern:

- Different logins for pe1, dev1, dev2
- Quay account creation (m3.3)
- SSO/OIDC setup (m2.5)
- Repeated login instructions

=== 4. Concept Introduction Pattern (~7 occurrences)
Pattern:

- Multi-paragraph explanation of concepts
- Often with diagrams
- Then transition to hands-on

*Examples*: m2.1, m3.1, m4.1, m6.1, m7.1

== Technical Assets & Environment Changes

=== A. Pre-configure More Out-of-the-Box

*Current state*: Modules 2-3 spend significant time on initial setup (SSO, user sync, basic plugins)

*Recommendation*: Pre-configure the "baseline" RHDH instance with:

- ✅ Keycloak integration already enabled
- ✅ Basic user/group sync configured
- ✅ OpenID Connect authentication working
- ✅ Core plugins (GitLab, TechDocs, Kubernetes) already installed

*New Module 2 focus*: "Customize Your Platform" instead of "Setup Your Platform"

- Start with working portal
- Focus on customization and extension
- *Time saved*: ~30-45 minutes

=== B. Simplify Security Module Setup

*Current*: Extensive manual configuration in Module 6

*Recommendation*: Pre-install Trusted Artifact Signer with:

- Fulcio, Rekor, TUF endpoints already configured
- Signing template already in catalog
- Pipeline verification step template ready to use

*New Module 6 focus*: Using security features, not configuring them +
*Time saved*: ~20-30 minutes

=== C. Create "Express Path" Alternatives

Add optional "skip ahead" checkpoints:

----
Module 2: "Already familiar with RHDH basics? Skip to Module 3"
Module 6: "Want to focus on developer experience? Security module is optional"
----

This allows:

- Shorter workshops (4-5 hours instead of full day)
- Flexible delivery for different audiences
- Self-paced learning with clear markers

=== D. Optimize Repository Structure

*Current*: Many small template repositories

*Recommendation*: Consider consolidating:

- Create single "parasol-templates" repo with multiple templates
- Reduce repo sprawl in GitLab
- Easier to maintain and update
- *Note*: This is optional, depends on demo preferences

== Content Style Improvements

=== A. Shift Balance: Show → Tell

Pattern to adopt:

❌ *Current (Module 6.1)*:
----
"Software Supply Chain Security refers to protecting the integrity..."
[4 paragraphs of explanation]
[Diagrams]
"Now let's see this in action..."
----

✅ *Recommended*:
----
"Your pipeline is building containers, but are they secure? Let's find out."
[Jump straight to scanning demo]
[After demo: "This used RHACS, which implements SLSA framework. Learn more: [link]"]
----

*Rationale*: Workshop attendees want to *see possibilities*, not get security certification

=== B. Use "Art of the Possible" Framing

Change module introductions:

- *From*: "In this module you'll learn about supply chain security..."
- *To*: "What if developers could see vulnerabilities before they commit? Let's add that to your portal."

Focus on *capabilities unlocked* rather than *concepts to learn*

=== C. Move Theory to Reference Documentation

Create companion reference docs with:

- Deep dives into concepts
- Architectural decisions explained
- Best practices and production considerations

Keep workshop focused on *demonstration and exploration*
